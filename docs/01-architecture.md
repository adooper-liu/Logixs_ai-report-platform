# 01 · 完整技术架构

## 1. 目标与假设

为公司内部多人提供跨业务域报表数据平台。输入可来自不同文件、工作表、目录、数据库与 API；处理过程可解释、可重放，AI 不参与每行数据的自由生成。

初始部署假设：单组织、多个项目/业务域、批处理为主、分钟/小时级更新；不承诺毫秒实时、无限数据规模或既有硬件性能。CDC 和分布式计算不是一期前提。跨公司 SaaS 多租户未来另行评估，不能把项目隔离误当完全租户隔离。

业务描述全部选填；发布的技术阻断来自明确规则而不是资料不齐。含义不明的输入可进入原始层、规范暂存层，但不可凭猜测覆盖正式目标或生成有歧义的正式指标。

## 2. 三层职责

| 层 | 核心对象 | 确定性职责 | AI 辅助职责 |
| --- | --- | --- | --- |
| L1 接入/规范 | Source、Stream、Batch、RuleSet、NormalizedDataset | 接收、解析、剖析、规范、质量检查、入仓 | 识别结构与格式、规则草案、漂移影响解释 |
| L2 建模/指标 | Model、Relation、Dimension、Metric、Release | 粒度验证、关联、汇总、指标编译与测试、发布 | 关系/模型候选、键候选、指标草案、测试建议 |
| L3 报表/分析 | SemanticCatalog、Query、Report | 权限过滤、只读查询、Superset、结果追踪 | 问数、报表草稿、解释和异常排查 |

共享能力：身份权限、元数据目录、版本、运行任务、血缘、质量结果、AI 网关、审计和运维。

## 3. 数据面与控制面

```text
文件批次 / 目录 / 数据库 / API
               |
       接入 Worker（最小只读凭据）
               |
     原始对象留存 + Batch manifest
               |
        解析 -> 本地剖析
               |
规则版本 -> 确定性清洗 -> 检查 -> 隔离错误记录
               |
      Arrow/Parquet + warehouse staging
               |
模型版本 -> PostgreSQL/dbt 建模 -> 指标/关联测试
               |
       同一 Release 的候选数据集
               |
       发布事务 -> 当前版本指针
               |
   只读发布视图 / 语义查询网关 -> Superset

控制面：Django API + 元数据库 + 中文 React 工作台
调度：DB outbox -> Celery/Redis -> 隔离 Worker -> DB 状态
AI：经权限过滤的结构/摘要 -> 建议 -> 契约校验 -> 试运行
```

AI 不持有任意仓库写权限。AI 无法直接跳过质量检查或发布事务。

## 4. 技术选型和边界

| 组件 | 选择 | 边界 |
| --- | --- | --- |
| 后端 | Python 3.12 + Django 5.2 LTS + DRF | 认证、项目对象权限、配置版本、任务 API；不在请求中处理大文件 |
| 前端 | React、TypeScript、Vite、查询缓存组件 | 主界面为任务/批次/异常/模型，不复制 BI 产品 |
| 编排 | Celery Worker/Beat + Redis | 简单 DAG 状态机由平台拥有；消息至少一次，不承诺 exactly-once |
| 权威任务状态 | PostgreSQL control DB | 唯一约束、lease、outbox、重试及人工操作记录 |
| 原始存储 | BlobStore 接口 | 开发本地目录；生产私有 S3 兼容对象存储，绑定 checksum 和对象版本 |
| 批处理 | Polars + Arrow/Parquet | 受内存/CPU/文件规模限制，支持惰性扫描和分块落盘 |
| 本地 SQL | DuckDB | 每任务独立数据库/连接/临时目录；不让 Superset 连接共享 .duckdb 文件 |
| 共享仓库 | PostgreSQL warehouse DB | 一期持久化规范表、模型和发布数据；容量证据触发升级，不预先引入分布式集群 |
| 建模 | 模型契约编译器 + dbt Core/Postgres | AI 提建议，编译器产生受控 SQL/dbt 测试；dbt 不是权限系统 |
| 语义目录 | 平台版本化模型/指标契约 | 唯一指标定义源；生成 BI 数据集，避免 BI 和平台两处手填公式 |
| AI | 官方 Anthropic Python SDK | 独立服务模块/队列；适配接口避免业务模型与厂商类型耦合 |
| 展示 | Apache Superset | 查询发布层；自有元数据库；不是 ETL 或质量执行器 |
| 可观测 | 结构化日志、指标、OpenTelemetry | 最初不必部署全部监控组件，日志字段与 trace 约定先统一 |

不同时搭建 FastAPI 与 Django 两套控制后端；不一期引入 Kubernetes、Kafka、Spark、向量数据库或多 Agent 集群。需要时以明确指标/需求升级。

DuckDB 和 Polars 使用统一规范类型；SQL 后端不能保证的运算必须明确拒绝而不是换引擎改变结果。数据类型/Decimal/时区边界用 golden tests 验证。

## 5. 运行部署

开发：独立虚拟环境；PostgreSQL/Redis/Superset 通过受支持的容器环境启动。现有 Windows 没有 Docker 时先按 P0 验证 WSL2/Docker 可用性，不沿用旧环境假装启动成功。

单机试点：Linux，反向代理 TLS，control API、前端、scheduler、worker pools、Postgres、Redis、对象存储、Superset。元数据库/仓库/Superset 元数据库可同一 Postgres 实例但不同 DB/账号；正式负载增长后分开实例。至少隔离解析进程、入仓写入角色、BI 只读角色。

Worker 队列：`ingest`、`transform`、`model`、`ai`，分别限并发和资源。AI 超时不能耗尽接入队列。调度器单 leader，任务执行仍以 DB lease 防并发重复。

## 6. 前端信息架构

1. 总览：任务新鲜度、失败、待补输入、当前发布版本；不是登记完成率。
2. 接入任务：来源、数据流、多个输入角色、接收方式、执行周期。
3. 批次中心：文件/抽取清单、覆盖范围、输入就绪、运行状态、重跑。
4. 数据预览与规范：样本、字段剖析、AI 建议、规则影响、错误隔离。
5. 模型工作区：事实/维度、键、关系、粒度、指标、试运行对账。
6. 发布与报表：release 清单、质量结果、数据集链接、回退、Superset。
7. 运行与异常：阶段日志、问题定位、规则版本、重试、告警。
8. 管理：项目/角色、连接凭据引用、资源配额、AI 数据外发策略。

普通上传不需要先填写来源问卷。首次可以通过“新建接入任务 -> 批量交文件/连接数据源”开始；识别结果后将文件绑定到稳定 stream。识别不确定时保留未分配输入，不靠文件名相似自动污染既有任务。

## 7. 领域扩展原则

平台通用能力不能包含物流字段清单。领域模板通过版本化配置提供，sales、support、inventory 等可独立安装。共享维度有作用域和有效期；不同业务域同名“状态”“订单”“组织”不得自动合并。

技术复用来自稳定接口、类型、规则、运行协议和测试，不来自把旧 V6 程序包装成通用引擎。
